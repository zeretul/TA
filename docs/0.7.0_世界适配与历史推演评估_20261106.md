## 1. 本次用户要求与结论

用户明确：共用战斗面板、探索面板、名称和AI用语应随世界包适配；历史模拟器应作为TA项目内第二款独立游戏，以玩家诏令、AI推演、季度反馈与模拟经营为中心，不融入现有个人冒险流程。

结论：
1. 当前底座已有世界绑定、独立题材规则、通信限制与存档隔离，不能说完全没有适配；但界面选择与术语仍有6类实际遗漏。
2. 历史推演可以纳入TA项目，共用应用外壳、模型接入与通用保存基础设施；需要独立页面、季度运行时、国家状态及存档类型，不能仅靠新增一个冒险世界包完成。
3. 建议重新组织现有自制素材与规则，保留有效模块，重做诏令解释和玩家主流程；不建议把旧Python整套界面直接嵌入后宣称已整合。
4. 下面的问题是本轮新发现。此前总表“没有已确认缺项”的结论不再覆盖这些适配遗漏。历史游戏仍是待决定的新产品方向，不列作现有冒险游戏缺失。

- 作者包communication=letter。
- CharacterChat在letter世界直接拒绝即时私聊，前端改为写信并加入主故事。

## 4. 确认的6类遗漏

### A1：西幻战斗主入口走错（优先修复）
web/src/features/interactive/components/StoryStage.tsx:77只把wuxia、space交给AdventureCombatPanel，遗漏fantasy。西幻自身的AdventureCombatPanel和后端规则已存在，主入口却进入修仙CombatWindowPanel，调用的读取/动作流程也不同。
影响：不是单纯标题不好看，可能展示不适用的修仙面板或读不到西幻交战。
建议：按本局战斗能力选择对应面板，同时校验冒险规则是否实际存在；未知模式不默认退回修仙。增加从主页面点击进入西幻交战的检查。

### A2：所有探索统一称“秘境”
web/src/i18n/locales/zh-CN/realmWindow.ts:52起的标题、打开/关闭、加载失败、空态、所在状态与入口列表均固定“秘境”；StoryStageControls和RealmWindowPanel直接使用。
影响：星海设施探索、武侠场所探索也带修仙口吻。
建议：凡人“秘境”，武侠可用“江湖探索”，星海“设施探索”，西幻“遗迹探索”；最终名称由世界包声明，可覆盖，通用回退用“探索”。

### A3：伴侣关系统一称“道侣”
characterWindow.relationship.partner固定翻译“道侣”；CharacterWindowPanel:440按关系kind直接取共用翻译。
影响：星海/武侠/西幻的正式伴侣也被叫作道侣。
建议：共用关系事实不变；凡人可显示道侣，其余按世界和已保存关系显示伴侣/配偶。不能因显示文案把恋人自动变成夫妻。

### A4：物品与能力详情统一写“功法”
entryDetails.ownedTitle、empty、category.techniques等带“功法”；OwnedEntryDetails:45对修仙和三种冒险规则共用同一标题。
影响：星海机械能力、科技与装备详情仍使用修仙词。
建议：按题材使用功法/武学/专长与技术/技艺与法术等作者词汇；无定义用“能力与物品”。只修共用入口，不改已有物品专名。

### A5：无线电群聊沿用围坐与在场话术
groupWindow.pickHint固定“围坐下来”，membersSummary使用reachable数量却说“人在场”；失联提示也写“不在场，听不到”。GroupWindowPanel:328、397、451有真实消费者。
影响：通信正确，但UI把远端接通误述为人在现场。
建议：由实际channel判断“现场交谈/无线电通信”，区分在场、可接通和失联，不能只按世界名字替换。

### A6：功能入口仍依赖固定模块ID
StoryStage:81与GameSettingsView:175以actor_state_id等于xiuxian-state判断亲密活动入口。world_gameplay_modules:17及后续逻辑会为含自定义制作法的修仙包生成world-actor-state-*。
影响：能力实际仍是修仙的自定义包可能被误隐藏入口。这是现有合法配置路径的代码缺口，本轮未新建模型故事复现。
建议：入口读取明确世界能力；不更改用户已定制的亲密提示词、演绎和资格规则。无此能力的世界仍不自动开放。

统一改法：世界包提供“实际能力”和“显示词汇”两类信息。前者决定能不能做及采用哪套操作；后者决定叫法。旧包缺字段用当前题材兼容值或中性词，不能默认为修仙。主界面、弹窗、移动端标题、空态、错误、提示、详情、AI上下文一起消费同一份本局配置。读取本局冻结配置，不用最新作者包覆盖旧档。

这类界面分流及显示需要少量代码接线；单改AI规则不能改变按钮和请求路径。AI规则负责题材表达、人物行为与世界常识，不负责伪装尚不存在的程序能力。

## 8. 不应原样搬入的实现与已核对的问题

1. 诏令路径偏关键词分发。app.py:686直接parse_edict(content)；_match_action_type:181先命中一个任务类别；engine.py:3877同样返回首个动作。隔离纯函数探针：“赈济陕西；操练边军；兴修水利”在引擎动作分发得到单一relief，不是三项意图。
2. 逐条账本不等于逐条实际执行。edict_ledger.py:134的attach_result会把一份整体成功结果套到全部非条件指令。内存探针使用三条指令和一个成功task_id，三条都成为applied；函数只取project_id，未承接该task_id。这个探针证明该函数行为，不假称运行了一整季。
3. 部分跨季异常被包装吞掉。engine.py:4459附近把推演异常变成simulation_error或None；上层事务能处理抛出的错误，但吞掉的错误不会自动触发整季回滚。迁移前要明确哪些错误中止结算。
4. 设计文档和代码状态漂移，南宋scaffold/active就是实例；旧验收记录也混有早期问题与追加修复，不能拿标题直接当当前完成证明。
5. UI包含大量部门、财政、军工、科技、长期项目、诏令归档等页面。复杂度本身不证明不好玩，但会稀释“下诏—看后果—再决策”的核心。优先压缩操作面，再逐步开放明细。

原版Steam官方近期公开更新也提到减少诏书指令意图丢失。这仅说明同类问题值得防范，不证明TA或用户旧项目已修复，也不代替本地证据。

## 9. 推荐产品形态：TA内第二款独立游戏

TA入口提供“冒险”和“历史推演”两个目的地。进入历史推演后，有自己的开始页、剧本选择、季度存档和主界面；不是给当前冒险人物增加一页国家管理。

共用：模型供应商/连接配置、流式响应、取消与重试、文本组件、语言主题、通用存储与诊断基础。
独立：国家/地区/军队/政策状态、季度时钟、政策待办、历史剧本、回合结算记录、存档命名空间与恢复。冒险与经营不互相读写状态，也不共用角色背包或修炼结算。

方案比较：
- 旧游戏窗口嵌进TA：适合短期演示，双进程、两套配置与存档、旧缺陷都留下，不推荐作为交付架构。
- TA内独立历史推演模块：共用成熟基础能力，重做政策运行时和界面；推荐。
- 全部重写为全历史/全国家沙盘平台：初期成本与规则范围过大，暂不建议。

## 10. AI为核心的季度流程

查看奏报与局势 → 可选召见/廷议 → 自然语言整份诏令 → AI拆解多项意图及条件 → 经办人和相关势力作出反应 → 提出季度结果与跨季变化 → 校验资源、时间、权限、状态一致性 → 一次正式保存 → AI按人物立场呈现反馈 → 下一季。

AI应实质承担：理解新颖政策与条件、选择执行路径、人物利益与执行偏差、应对局势、外交和事件因果、长期政策修订、奏报表达。
代码保留必要职责：资源不可凭空复制、已花银粮实际扣除、同一季不能结算两次、任务持续保存、失败可恢复、信息受众受限。代码不是“每条诏令一个if”；AI也不能一句话直接把国家状态宣布成功。

复杂诏令先给玩家简短“拟办事项”供检查，明确重大歧义；正常明确命令不重复审批。例：先拨银修渠，待春汛前验收后减赋——必须保存修渠、期限和条件减赋三者联系，不能第一季全部算成功。

主界面建议只保留：本季三件要事、简洁国势/地图、奏报、召见/廷议、诏令和长期政策。财税/军事明细可展开；不强迫玩家每季点遍30个页面。

## 11. 首个可评审范围与风险

先做单一明末剧本的一段完整季度循环，保留已有南宋资料供后续复用：
- 一次诏令包含多条命令、条件与先后顺序。
- 至少一个跨四季项目，可追加资金、换人、暂停、核查。
- 银/粮/军费存在相互制约，官员不同会影响执行。
- 至少一条未处理会发展、及时干预会改变的危机。
- 新档、保存、重开、分支与失败重试可用。
- 用本机模型检查自然诏令和报告，不能只用模板或规则直调宣称AI玩法完成。

关键风险及补救：
1. AI变成固定按钮的包装：检查同义表达、三条混合命令和新政策是否真的改变后续状态。
2. AI无限迎合：执行阻力必须来自人物、资源和时代条件，失败有可追溯原因，不用随意拒绝制造难度。
3. 谎报变成瞎猜：重大谎报要留下核查渠道和代价，平常事项不处处造假。
4. 双游戏共用错误数据：存档类型与状态模型独立，恢复时校验游戏类别与剧本版本。
5. 单季等待太长：只推演受影响实体，批量报告、复用稳定设定、支持取消恢复；避免每个省每个官员都单独调用模型。
