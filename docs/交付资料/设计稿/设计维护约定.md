# 设计文档维护约定

适用版本：0.7.0起；更新：2026-11-05。

## 一份现行说明，一份可追溯原稿

现行规则按主题写在本目录；具体批次结果放docs的交付报告，历史设计和素材放资料归档。不要再次把聊天流水、施工分工、旧失败日志和重复总表堆进现行设计。

归纳稿未逐条展开的原稿细节不因此作废，也不自动算已实现；查到已确认的具体要求时仍须对照代码，保留差异。

新增或修改设计默认写清四件事：玩家能得到什么；规则与AI/程序分别负责什么；与已有记录、界面和世界的衔接；当前实现、明确差异及依据。仅在复杂行为需要时增加流程表，不套长篇模板。

## 状态用语

- **当前行为**：有当前代码或内容消费者支持，并指出入口；不等于自然模型全程已验。
- **设计要求**：用户已确认的目标；未实现就明确写差异，不擅自降为可选扩展。
- **已取消/已替代**：有明确后续决定，保留原因和原稿入口，不能靠编辑文档自行取消。
- **讨论/扩展**：尚未确认范围的建议，不自动派工、不放当前缺项栏。
- **验证记录**：分清源码静态、规则测试、真实模型、浏览器及正式程序读回；不因存在测试文件就写“通过”。

## 每次实际修改后

更新对应主题的当前行为与边界、必要源码/提示词入口、关联报告和逐稿索引。应用版本变化或作者目录变化时同步总览与四世界表。若只是文档维护，不改应用版本、程序、模型或玩家档案。

记录实际缺失行为，不把长期试玩、未穷尽组合、外部发布决策或更多可选内容当成缺项。发现已确认但未实现的要求时明确列出具体影响；未核实的疑点先标疑点，不编造已完成状态。

保留用户备注、原始素材和下载件；不要整包覆盖当前作者内容。旧Git提交、历史设计行号与旧候选路径都不能代替当前源码。

## 规则优先

优先修改已有AI规则和内容，只有缺少必要结果或保存能力时补最小代码。内部提示优先中文；玩家正文自然表达，不展示审批条款、内部ID或实现说明。原始设计的数值和API细节若已由运行规则拥有，文档链接到实际来源，避免双份长期漂移。
