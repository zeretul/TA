# NOTION 云端开发任务书

日期：2026-11-10。这份文件是给云端开发方（NOTION）的任务书。**请从头读完再动手**，尤其是"硬性边界"一节——那里的约束来自项目长期约定，违反会被要求返工。

## 你的任务

在 Text Adventure（下称 TA）0.7.0 源码上，完成**斗破苍穹、哈利波特、诡秘之主**三个世界的机制适配，即 WP-01 到 WP-07 **全部七项**。

这七项都是待办，都要做。但"做"的含义按项不同：

- **WP-01、WP-02 是内容工作**：确定范围、写世界书、写状态映射。产出是文档与包内内容。
- **WP-03、WP-04、WP-05 是验证工作**：先复现现有能力能否承接，**只有复现证明有缺口才补通用代码**。产出是验证记录 + 必要的通用补强。
- **WP-06 是验收工作**：三个世界各做最小样例，跑反例清单。产出是真实模型证据。
- **WP-07 是收口**：汇总归类 + 回归已有四个世界。产出是结论 + 回归结果。

**不要把它理解成"造三个世界的专用系统"。** 这个任务的核心判断是：哪些能靠世界书 + AI 推演 + 现有状态承接，哪些确实需要补通用能力。大部分机制应该落在前者。

## 第一步：拿代码

仓库：`https://github.com/zeretul/TA`（私有，需要授权）

```bash
git clone https://github.com/zeretul/TA.git
cd TA
```

**不要克隆后就地大改。** 按下面方式挑你需要的东西：

- **代码全都要**：根 module + `agent/` 子 module 都在仓库里，两者是独立 Go module，必须分别构建。
- **文档挑着读**：`docs/` 有 160+ 份文件，其中**大部分是历史交付记录**，路径和结论都过期了。先读 `docs/文档地图_当前设计与历史记录.md`，它标明了哪些是当前设计、哪些只是历史现场记录。按错文档做决策会重复造轮子或推翻已定方案。
- **前端产物要自己生成**：仓库不含 `web/dist` 和 `internal/webfs/dist`，跑 `pnpm --dir web build` 生成。
- **`.gitignore` 会挡 `docs/`**：仓库已配好放行规则，但如果你新增文档被忽略，检查 `.gitignore` 里的 `!docs/...` 段。

## 第三步：七项任务怎么落地

### WP-01 划定范围

为三个世界各确定：原作版本、年代、区域、可玩阶段、角色起点。把**原作规则、游戏化约定、未核实设定**三样分开写。

哈利波特的自由时间旅行、诡秘之主的无限制高序列因果改写**明确列在范围外**，不要实现。

**完成标准**：每个样例都有明确范围和不支持项清单；不混用小说、影视、游戏、同人规则。

### WP-02 世界书与状态映射

为每个世界整理机制清单，每条必须说明：前提、例外、代价、失败后果、需要读取/保存的事实、规则如何取用。

重点映射（详见分析文档的机制表）：
- **斗破**：境界/星级、功法、异火持有与炼化、炼药
- **哈利波特**：已学咒语、魔杖持有/忠诚、真实身份/伪装、效果期限
- **诡秘**：途径/序列、扮演依据、晋升条件、污染来源、封印物代价、知情事实

**先复用现有对象/列表与正式提交。拒绝只写正文不落状态的实现。**

**完成标准**：每条机制说明前提、例外、代价、失败后果、需保存的事实及取用方式。

### WP-03 条件知情（验证优先，缺则补）

复现当前知情门槛的缺口，提出按"本局授权 / 已获线索 / 世界自定义阶段"过滤资料的最小方案。要区分三种知识：**裁判知道什么、主角知道什么、各 NPC 知道什么**。

这是三个世界里**最可能真需要补代码**的一项。现有资料硬门槛只有修仙最低阶段和地点，不支持任意授权/途径/序列/线索组合。但先复现，用证据决定补多少。

**完成标准**：搜索、按 ID 读取、常驻上下文、人物聊天的边界一致；权限变化可追溯；重开/分支不串知情。不能把 private 界面标记当作全部知识权限。

### WP-04 持续效果（验证优先，缺则补）

用复方汤剂和封印物代价验证现有持续效果记录。覆盖：开始、期限、解除、跨期等待、周期代价、多效果并存、失败重试、重开。

**用现有正式时钟与提交，不新增第二套时钟。** 条件语义仍由 AI 判断，只补必要的记账与一致性保证。

**完成标准**：到期不漏、重试不重复、分支不串。

### WP-05 成长结构边界（判断为主）

验证斗破境界、诡秘序列能否用通用状态表达。明确回答三个问题：
1. 现有数值模块能复用到哪里？
2. 是否真的需要固定计算？
3. 规则 + AI 是否已经足够？

**不要换名套用炼气/筑基结构，也不要用普通经验升级冒充。** 新能力通过已有集合字段扩展。

**完成标准**：若规则 + AI 足够则**关闭**程序扩展项，不为了"看起来做完了"硬造计算器。只有明确要求固定结算，才设计包定义阶段的通用能力。

### WP-06 最小验证样例（验收）

三个世界**分别**做最小样例，执行分析文档里的反例清单：

| 世界 | 场景 | 应观察到 |
| --- | --- | --- |
| 斗破 | 获得异火但未炼化；未学焚诀却要求功法自动进化 | 持有与掌控分开；特殊资格不自动赠送 |
| 斗破 | 炼药材料不足；炼制失败后重试/重开 | 不凭空生成材料或成品；消耗与失败只提交一次 |
| 哈利波特 | 复方伪装期间与知情/不知情人物分别交谈，再等待到期 | 真实身份不变，反应有区别；到期有正式时间依据 |
| 哈利波特 | 禁止幻影移形区域尝试移动 | 先处理规则前提，不能高骰点抹掉限制；拒绝后位置正确 |
| 诡秘 | 只有玩家声明"我完成了扮演/仪式"，本局无相应事实 | 不因声明自动消化/晋升；能说明缺失事实 |
| 诡秘 | 未授权者搜索、猜 ID、聊天间接追问同一秘密 | 各路径保持同一知情边界，不靠换入口泄漏 |
| 诡秘 | 携带持续代价的封印物，跨期限后重开和分支 | 代价不漏不重复；支线不污染主线 |

另加：取消/重试、冷重开、分支隔离。

**必须保留真实模型输入输出、正式状态和重开证据。AI 正文写得对但实际状态错 = 失败。三个世界分别验收，不能用一个世界通过代替其余。**

### WP-07 汇总与回归

汇总哪些问题靠世界书修正、哪些靠配置、哪些确需通用代码。实现后的代码改动按影响做回归，**复核四个已有世界**（凡人修仙、武侠、星海、西幻）与自定义通用世界。

**完成标准**：不引入世界名分支，不泄漏专有规则，不破坏可选判定与包绑定。

## 硬性边界

这些是项目长期约定，不是建议。违反会被要求返工。

### 架构

- `agent/` 是独立的 Native Agent Runtime，**不感知外部 runtime**。不要通过给它注入外部 runtime 来实现切换。
- 多 runtime 能力聚合在 `internal/agents/runtime`，不新增 Go module。
- 游戏**不支持 Goal**。UI、API、执行层都不得开启。
- **不引入世界名分支**（不要写 `if world == "斗破"`）。专有规则放在世界包内容里，不写进代码。

### 明确不做的

做 WP-01—07 **不等于**放开下面这些：

- 三个专用战斗/升级/污染引擎
- 任意规则脚本引擎
- 自由时间旅行
- 没有实际需求的中途顶层 schema 扩展
- 每日任务、签到、重复刷次数、现实等待
- 把普通生活、关系、组织、制作做成合同、审批、清单

### 数据与配置

- 不新增第二套时钟、第二套 Todo、第二套 Goal。
- 每个注入片段必须有明确来源、用途、容量上限，并说明超限处理。
- 用户内容的自动迁移/重命名/删除必须有回滚路径或备份。
- 受管 Project 以稳定 `ProjectID` 为身份；路径持久化为 `/` 分隔的相对路径；宿主绝对路径不得写入 Registry/Session/metadata。

### 语言

- 模型可见内容（提示词、上下文片段、工具说明、schema 自然语言）用**中文**，不重复注入双语。
- 代码标识、JSON 字段、协议枚举、模型 ID 保留原样。
- 用户可见交互、错误、空状态需要**独立的中英文资源**，按当前语言单语展示。
- 注释、日志、内部错误、终端输出用**英文**。

### 交付

- **不要发布、不要打 Release、不要把仓库转公开。** 这是私有开发仓库。
- 不附带密钥、存档、依赖目录、`dev-data`、`.ta-game`、`config.toml`。
- 不因拿到源码就自动同步到任何安装目录。

## 验证要求

先安装依赖：

```bash
go mod download
(cd agent && go mod download)
pnpm --dir web install --frozen-lockfile
```

按影响范围运行，结果如实记录：

```bash
go test ./...
go vet ./...
(cd agent && go test ./... && go vet ./...)
pnpm --dir web check:i18n
pnpm --dir web test:unit
pnpm --dir web build
```

注意：
- 根 module 的 `internal/app` 包测试**很慢**（数百秒级）。如果看到 `panic: test timed out` 且耗时正好约 600 秒，那是 go test 默认超时，不是代码缺陷。改用：

```bash
go test ./internal/app -timeout 1800s
```

- 涉及 UI 必须打开页面验证，检查窄屏、宽屏、长文本、空数据、明暗两种主题。
- 涉及模型要记录**实际模型调用结果**。未配置模型不能算通过。
- 测试用独立数据目录与端口，不复用真实数据。
- 两个 module 都要跑；只跑根 module 不算全量。

## 交付与合并

你的改动最终要合回本地开发库，所以：

- **一个逻辑改动一个提交**，commit message 用**英文**，说明为什么改而不是改了什么。
- 不要 `git reset`、不要强制推送、不要改写历史。
- 不要用整个包覆盖式提交（会冲掉本地其他改动）。按文件、按稳定 ID 合并。
- 交付时提供：源码差异、实际验证结果、**未验证项和原因**。
- 状态**逐项**标注，用这三个词：`规则已整理` / `样例已验证` / `必要能力已实现`。
  **不能统一写成"适配全部完成"。** WP-05 判定不需要程序扩展时，如实写"规则 + AI 足够，不补代码"，这也是有效结果。

## 参考：为什么先验证再补代码

分析文档已经指出现有能力的三类情况：

- **规则可承接**：资料读取、人物事实、状态对象/列表、道具记录、事件、正式提交，能表达所需结果。
- **有限复用**：已有计算器只支持其明确的数据结构、效果种类和公式；改包内参数不会改变计算语义。
- **能力缺口**：当玩法要求程序保证任意条件权限、持续效果生命周期或特殊因果一致性时，当前能力不足。

所以 WP-03、WP-04 这类"缺口项"的正确做法是：**先复现，用证据说明缺到什么程度，再决定补什么**。不要一上来就设计一套完整系统。
