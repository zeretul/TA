## 三、验收方法（本次如何取得证据）

验收脚本：`web/scripts/style-acceptance.mjs`，由 `web/scripts/run-style-acceptance.mjs` 驱动。它起一个**只转发、不改写**的记录代理挡在真实网关前（`web/scripts/recording-model-proxy.mjs`），后端指向该代理，数据根落在 `web/test-results/style/`，端口 19740/19741，跑完自停。记录里**不含** Authorization、密钥、完整提示与思考正文，只留请求形状、系统提示的 SHA-256 与字节数、各用途片段的标题／字数／SHA／短摘录，以及助手正文的摘录。

STY-07 的**真实进程重启**由 `web/scripts/style-restart-acceptance.mjs` 单独验收：它自建 `denova-restart.exe`（`-tags embedweb`），数据根落在 `web/test-results/restart/`，端口 19742，先经真实接口写入三用途并核对已落盘，再杀进程、等端口不再应答、用**同一数据根**冷启动新进程读回设置，重复一轮以验证单项重置。结果落在 `web/test-results/restart/restart-acceptance-result.json`。

结果：`==== 文风验收：31/31 通过 ====`（真实后端＋真实浏览器＋真实模型网关，故事 `st_dm51zkiw8bic129bcfe8`）。

**复跑状态（2026-10-16）**：在当前提交上复跑时，脚本先后暴露出**两处验收脚本自身的缺陷**（见下第四节第 4、5 条）。第一次复跑（只修了第 4 条）进程**被中途打断**（进程退出码 4，止于第 37 个请求，未打印汇总），不构成证据。第二次复跑（仍只修了第 4 条）完整跑完，得 **29/31**（进程退出码 1）：29 项通过，2 项失败——「每一类都产生了自己的主叙事片段」缺 5 类、「十二类主叙事片段两两不同」只剩 7 个。诊断见第 5 条：失败源于脚本自己把上下文窗口写成 100000（产品默认 400000），压缩硬发布带因此只有 85000，十二回合后请求压不下去，后五类回合根本没有提交。**这是脚本缺陷导致的失败，不是产品缺陷**。

**修好第 5 条后第三次复跑（2026-10-16，真实后端＋真实浏览器＋真实模型网关，故事 `st_dm69fwgqsvj8b40dee25`）：`==== 文风验收：31/31 通过 ====`，进程退出码 0，31 项断言全过、无 FAIL、压缩失败 0 条。** 修正口径后的关键读数：

- 「十二类主叙事片段两两不同（不是同一份提示换名）」→ **12 个不同片段 / 12 类**；
- 「每一类都产生了自己的主叙事片段」→ **12 类**全有；
- 「抽样两类正文并非同一段文字」→ `strange-tales` **1146 字**、`flippant-banter` **1432 字**。这两个数字是第 4 条缺陷修正后的**真实正文字数**（修正前被虚报为 3785／4038 字，因为把检查点文档与其后所有回合都算了进去）；复核线上正文确认取到的确是给读者看的叙事，不是 `# 续写检查点`／`## Goal` 规划稿。

因此本批文风线的结论是：**在修复后的脚本口径下，31/31 通过**，且上下文窗口与产品默认一致（`400000`）时不会在十二回合处触顶。

### 过程中先修掉的五处「验收脚本自身」缺陷

这五处都不是产品缺陷，但都会让数字说谎，所以修好之后才记分：

1. **读故事记录失败被静默吞掉**。`storySummary()` 原把读取失败降级为 `{}`，于是 4 条失败看起来像「字段未设置」。改为 5 次重试＋`__unreadable` 显式标记，调用点直接报「故事记录读取失败」并附诊断。
2. **片段字数被放大 36 倍**。记录代理按标题切片，最后一段的终止符写的是 `# Text Adventure Built-in System Instruction`；而该标题是**加在第一个内置片段之前**的，内建工作流片段本身没有任何前缀，于是最后一段一直吃到内建工作流末尾。实测：主叙事被报成 **22379 字**，真实只有 **621 字**。改用工作流的首句作锚点后，数字回落到 621／623／875／883。
3. **两条断言本身写错了**。其一，`json:"combat,omitempty"` 决定了「跟随主叙事」是**键缺失**而不是空串，原断言却要求 `combat === ''`，即要求一个 schema 从不承诺的形状——改为断言语义（该用途不再指定文风），并以「下一请求不再携带战斗片段」作为落盘层面的证据。其二，世界贴合度用了一份**硬编码的民国词表**且只看正文前 400 字，于是点名了沈曼青、走在霞飞路上的正文仍被判为「不贴合」；改为**从本次安装的剧本包自带 lore 读取**人物与关键词，并分开报告「人物／地点」与「世界词」。
4. **抽样「正文」取的不是那一类的正文**（本次复跑才发现）。原 `proseAfter(requestId)` 取的是**该请求之后记录到的全部响应**并拼接，于是「`strange-tales` 的正文」实际包含：本回合的**检查点文档**（模型先输出的 `# 续写检查点`／`## Goal` 规划稿，不是给读者看的正文）、本回合真正的正文，以及**其后每一个回合**——包括其它十一类各自的输出。它报出的 3785／4038 字因此不是那两类的正文字数。改为按**本回合自己的请求 id 列表**取，并跳过检查点文档（判定依据是正文开头的「检查点」标题或 `Goal` 段）。修正后每一类只算自己那一回合的正文。
5. **验收自己把上下文窗口写小了四倍，于是撞的是自造的天花板**（修好第 4 条后复跑才发现）。`web/scripts/run-style-acceptance.mjs` 在隔离配置里写死 `context_window_tokens = 100000`，而产品的默认值是 `config.DefaultContextWindowTokens = 400000`（`config/model_profiles.go:12`）。压缩的「硬发布带」是 `上下文窗口 × 阈值`＝`100000 × 0.85 = 85000`（`agent/definition_compaction.go:459`），于是一局连跑十二类、历史累积到约 8.7 万 token 后，压缩**无法把请求压回 8.5 万以下**，后续回合不再提交：驱动端表现为最后五类各等满 420 秒仍未推进，报「缺失 intrigue-ensemble、slice-banter、hotblooded-combat、cinematic-shots、dialogue-piece」，另一条「12 个片段两两不同」随之只剩 7 个。日志里 8 条 `automatic Agent Compaction failed` 中有 6 条是 `… remains above hard publish band: after=87456/90284/90804/91279/91340/92719 limit=85000`，全是这个自造上限造成的（另 2 条是 `Compaction model returned an invalid checkpoint`）。改为与产品默认一致（`400000`，并留 `DENOVA_STYLE_CONTEXT_WINDOW` 可覆盖）。**这是验收脚本的缺陷，不是产品缺陷**：产品真实默认窗口下不会在十二回合处触顶。
