更新：2026-11-06。范围：只读研究本地《历史模拟器：崇祯》客户端的实际运行代码、接口声明与少量配置。没有启动官方客户端、发出账号/模型/服务器请求、读取私人存档或凭证，也没有查看或复制图片、模型、美术及整包源码。

**用户最新方向优先：模拟经营同样采用“通用底座＋剧本包”；玩家可以先找大臣讨论，也可以直接下诏；AI结合全局局势推演，按季度汇报；玩家据此修订或者继续既有命令。后续先明确这些规则，现有明末工程首片暂作验证原型，不继续用新增固定动作来代替这一方向。** 本文只提供原版证据与可借鉴的分工，不声称已经获知官方服务器的完整规则。

## 1. 原版确实具有剧本身份与内容覆盖通道

**已确认的运行事实：**

- R:52401–52424保存当前 `scenario_mod_id`，默认剧本身份是 `official-chongzhen-v1`；普通API通过 `X-Scenario-Id` 路由剧本。流式聊天另在 `buildStreamHeaders` 中携带加密剧本身份，不是只有普通请求支持剧本。见R:60672、60764、64013。
- `service.scenario.checkVersion`调用 `/scenario/check-version`；R:66024的独立状态保存版本信息。剧本失效时客户端关闭对应Mod、回退默认身份并提示重启，见R:60719。
- R:70413的实际页面加载 `game-config.json`、`key-events.json`、大臣提示词预设、廷议快捷文本、页面指引和 `global_config.json`。它们不是单纯说明文档，而有解析函数与状态消费者。
- 日历规则支持纪年列表、每年季节、数字形式、开局前回合、纪年切换及正逆序年份；`getTurnTextFromConfig`在R:48171。全局显示配置提供 `edict_opening_phrase` 与 `main_regime_code_name`，见R:48361。
- 客户端剧本字段定义还包括初始任务、事件预测、长期国策提示、特殊推演、随机事件链等。例如R:55232 `events_prediction`、55256 `initial_tasks`、55375 `long_term_prompt`、55524 `random_events_chain`、55637 `special_simulations`。这是内容定义面的证据，不等于看到了每个字段的服务器执行实现。

**对TA的意义：** 通用循环、保存、模型调度和信息呈现属于底座；纪年、地域、人物、政权、开局局势、事件及时代规则属于剧本。不能把明末人物和1627纪年写成所有经营剧本共享的事实。

**不可扩大：** 原版并非证明了“任何题材都零适配”。R:123066的季度重心请求仍有 `current_year + 1627`，说明其中存在明末专用残留，不能照搬为通用底座规则。

## 2. 大臣讨论是独立可选入口，历史与上下文主要由服务器组织

| 路径 | 客户端实际请求/返回 |
| --- | --- |
| 普通私聊 | R:100871发送 `npc_name`、`message`，命中预设时另带 `actual_message`；由 `/npc/chat/stream`返回流式正文 |
| 私聊历史 | `getChatHistory(npc_name)`读取 `/npc/chat/history`，页面按人物名称装入历史，R:64095、101020 |
| BYOK私聊 | `/byok/npc/chat/prepare`返回 `session_id`、`llm_request`；客户端调用模型，再以 `full_response`、`model`、`usage`提交finalize，R:64500、100908–100916 |
| 记忆压缩 | 私聊BYOK路径先异步请求 `/byok/memory-compression/check`；按返回的 `turns[].turn_index/llm_request`生成摘要，再提交 `summaries`，R:100894–100902 |
| 廷议 | 本地这一版界面要求两位大臣；BYOK以 `discussion_id`、`player_message`开始，服务器逐轮返回发言请求，客户端回传 `session_id`、`round_response`，R:102695、102743–102748 |
| 廷议总结与历史 | `summary/prepare`按讨论ID返回 `minister_a`、`minister_b`的模型请求，`summary/finalize`提交对应回答；另有 `/npc/court-discussion/player-history`读取讨论记录，R:102812–102825、97907 |

**能确认：** 原版有跨请求保存的私聊/廷议历史及压缩通道，不能说它完全没有记忆机制。讨论也不是游戏推进的前置必需步骤。

**不能确认：** 请求没有由前端显式拼装全国状态，不代表模型没有获得全国状态；可能由服务器从账号与剧本状态装入。相反，也不能仅凭 `llm_request` 这个字段就断言每位大臣都获得正确、最新、按权限过滤的情报。后台检索、遗忘策略、当前数字覆盖旧数、私聊受众隔离和压缩摘要保真，本轮都没有服务器实现证据。

长记忆修改前的拟旨预设偏重本季主题；当前本地版本修改了这一措辞。但这只证明提示词变化，不能替代对长期命令事实源的维护，也不能直接证明官方会删除旧命令。

## 3. 讨论结果通过“建议库”进入下诏，不是所有谈话自动执行

运行链条可定位为：

1. 私聊里将一段答复标记为建议。`useSuggestionSave`调用 `saveNpcSuggestions(suggestion,npc_name)`，R:101181；接口是 `/npc/player/npcs/suggestions`，R:61199。
2. 诏书案头的 `AdviceLibrary`查询当前 `turn_number` 的建议，并可单独删除建议，R:105609–105616。这里“删除建议”是删除建议记录，不是撤销国家政策。
3. 选择建议后，文本被追加到主诏书输入，或军事、内政、外交、其他分类输入，R:105624–105634。
4. 廷议有独立总结返回；界面形成的建议和主诏书仍须由玩家选择、修改和发布。

**可借鉴规则：** 讨论、建议、拟旨、正式命令应有明确身份与来源。AI建议不是已经扣款、已任命或已改变政策；玩家可以接受其中一部分，也可以绕过讨论直接写命令。这比要求每次操作都经过一个大臣按钮更接近原版的自由下诏流程。

## 4. 直接下诏成立，润色可选；季度推进应按真实消费者理解

- R:52356定义军事、内政、外交、其他、主诏书和润色前文本的独立草稿状态；`useEdictContent`在R:105938组合这些文本。这是输入组织，不是只能执行四类固定动作的枚举合同。
- 润色调用 `/game/edict/refine`；BYOK则为 `/byok/edict/refine/prepare` → 模型 → `refine/finalize`。其职责是把玩家计划整成诏书，不等于正式执行。接口在R:61053、64510。
- R:106700–106728的发布消费者直接使用主诏书；没有主诏书时组合分类输入，**没有要求必须先找大臣或先润色**。
- 发布先调用 `shotTurnNumber({player_id})`，即 `/tradition/player-state/shot-turn-number`；随后执行 `confirmEdict({player_id,edict_content})`或BYOK推演循环，同时将界面引向下一季度重心，R:106735–106753。
- 客户端也声明了 `/game/turn/advance/{player_id}`包装，但本轮定位到的发布主消费者不是简单调用这个包装。不能只看到函数名就把它写成实际推进顺序。
- 季度重心是原版的额外机制：三个“月份”槽选择领域，向 `set_current_category3`提交类别和回合；随机/普通事件另有 `event_key`、`option_index`与批量效果请求。它和下诏主循环相邻，但不是TA必须照搬的规则。

**可借鉴规则：** 玩家入口可以只有自然语言命令、可选讨论、核对和发布。程序要管正式命令何时进入推演、何时完成一个季度，不能因界面换页就默认推演已成功；具体回合原子性仍须由TA自己的事实保存保证。

## 5. 原版AI推演是多阶段编排，客户端不是“算好结果后让AI润色”

`runEdictConfirmLoop`在R:64860，且在长记忆修改前备份中已存在。实际BYOK合同如下：

| 阶段 | 可见字段与责任 |
| --- | --- |
| 启动 | `confirmStart({edict_content})`返回 `session_id`、`seq`、`phase`和首轮 `request` |
| 推演迭代 | 客户端依 `request.role`选择模型，执行服务器给出的请求；回传 `confirmAdvance({session_id,seq,response})` |
| 继续 | 服务端返回下一轮 `request/seq`与 `phase=loop`，客户端继续调用；不是前端固定赈济、练兵、建设三个分支 |
| 汇总 | `phase=finalize`返回 `finalize_requests`，分为 `output_generation`、`task_management`、`event_management`；客户端分别完成，再以 `phase2_responses`提交 `confirmFinalize` |
| 终局 | 可以转入 `endgame`，另取 `endgame_request`并调用 `endgameFinalize`；返回终局文本/状态 |
| 异常 | 会话ID贯穿流程；未到finalize前的错误尝试调用 `/byok/session/abort`。存在步数与超时保护；本轮没有验证服务器是否真正回滚所有中间状态 |

客户端 `buildByokRequestBody`（R:64659）保留服务器发来的 `messages/tools` 等请求内容，只替换模型、流式标记及允许的模型参数；保护项禁止用户参数覆盖 `messages/tools/stream/model`。`singleRoundCall`将模型回答、tool calls与用量作为响应信封回传。**模型在推演链里承担实质任务；任务和事件也有各自的AI处理阶段。**

**关于“依据全局局势”：** 启动请求主要是命令文本，全球信息与模型工具由服务端准备，客户端没有展开完整国家上下文。可以确认“状态在服务端、推演请求由服务端组织”的分工；不能确认它每轮具体读取了哪些地区、政权、军队、财政、已生效政策和历史，也不能推断其数值结算公式。未调用真实API，本轮没有任何服务器返回的实际 `messages/tools` 样本。另按包内静态文本的规则/剧本/提示词文件名定向核对，只定位到省份字段schema和大臣拟旨预设，没有发现可直接读取的官方全局推演提示词文件；这不是对所有隐藏实现的穷尽证明。

**对TA的直接边界：** 目前三类工程及有限效率变化只证明保存和短周期能工作，不能代表已经实现这种通用AI经营推演。后续应先写全局局势、持续命令、执行者、影响链、时序与报告的规则，再决定最少需要哪些正式状态和提交接口。

## 6. 季度报告、国家详情、任务和事件是分开的产品结果

- `/game/turn-edicts`提供按回合的诏令记录，包含 `turn_number` 与 `turn_result`。`ViewMemorialModal`按回合排序/选择，`MemorialContent`取上一回合的 `turn_result`并作为朝政形势正文显示，R:98093–98117、105699–105713。
- 奏疏页提供直接打开议事和诏书页的消费者，R:98120–98123；由此可以“读结果→问大臣”或“读结果→直接改命令”。
- 国势数据另有 `/v1/overview/status`、`/v1/provinces`、`/v1/troops`、`/v1/parties`、`/v1/social-classes`、`/v1/regimes`等查询，R:64227–64274；不能把一篇奏报当作唯一世界状态。
- 时政任务有 `/task/player/tasks`、`/task/detail`、`/task/history`；事件有摘要、未来皇帝事件与过去事件接口，R:61155、64309。
- BYOK结束阶段将正文生成、任务管理、事件管理分开；说明客户端合同中至少存在不同结果职责，不能把任务列表等同于正文的关键词摘录。

**结构化与叙事的界限：** 客户端已确认“回合容器＋叙事正文＋独立国家详情/任务/事件”。尚不能据此声称已看到官方完整的结构化结算账本、资源守恒检查或回合差量schema。普通 `turn-edicts[].turn_result`的展示正文，与终局返回里包含 `is_game_over` 的对象也不应混成一种固定结构。

## 7. 旧命令的继续、修订与撤销，必须分清四种东西

| 对象 | 原版可见证据 | 本轮不能据此推导的事 |
| --- | --- | --- |
| 编辑框草稿与润色撤回 | `PrevImperialEdictContentAtom`与R:106770交换当前/前一版文本；发布成功调用 `useResetEdictContents`清草稿（R:66253、106065） | 清空草稿或撤回润色，不是撤销已生效政令，也不证明旧命令自动失效 |
| 以前颁布的诏书和结果 | `/game/turn-edicts`及历史查看入口保留过去各季记录 | 保存旧全文，不等于一定把其中未完成命令注入下一次推演 |
| 已解锁的长期国策效果 | `/tradition/perks/long_term_perks_influence`被长期政策页面与诏书案头实际消费；字段元数据有 `long_term_prompt`，R:64188、103751、105480、55375 | 这里的“国策树长期效果”不能直接等同于所有自然语言诏令的持续台账 |
| 本轮地区/军队操作与事件摘要 | `/v1/events/map-commands/create/list`按 `target_type/target_id`组织；撤销调用 `/v1/events/revoke`并带 `summary_key`，R:64288–64304、65758、65850 | 已观察到的撤销操作不能泛化成任意长期国策的完整撤销/资源返还机制 |

客户端还存在未来皇帝事件、已发生事件和AI任务/事件管理阶段；这些为持续事务提供了可能的载体。但本轮没有找到可核验的通用自然语言“有效命令集合”的完整schema，也没有官方服务器的新旧命令冲突解决、到期、暂停、修订、取代和撤销实现。因此不能声称原版保证“下过一次就永久自动续行”，也不能声称它完全不支持。

**TA规则需要明确写出的部分：** 玩家说“继续”时应继续本局仍有效且条件满足的命令；新命令可以补充、修改或明确替代旧命令；本季没重写的持续命令不能仅因没出现在输入框而丢失。完成、取消、暂停、等待条件和持续执行应能区分。它们需要可追溯的事实保存，AI据此解释和推演，不依赖每季复述整段聊天。这是用户要求下TA应明确的规则，不冒称已从官方源码抄到答案。

## 8. 可确认的原版取向与仍然未知的关键处

可以采用的取向是：**通用季度外壳＋剧本身份和内容；可选议事；自由命令；服务端依据本局状态组织AI推演；叙事、任务、事件、国势各有来源；玩家读报后再问、再改或继续。** 原版提供的证据比“固定工程按钮＋AI写奏报”更丰富。

以下仍是未知，不应在TA规则中以“原版就是这样”替代设计：

- 全局局势上下文的真实组成、检索范围、不同AI角色分工及token容量。
- 各大臣的知识权限、记忆压缩保真、旧事实被新事实覆盖与保密边界。
- 自由命令的有效期、冲突/继承/撤销规则和服务器资源结算公式。
- 同一季度多阶段写入的事务性，以及失败中止能否完整回滚。
- 所有剧本内容是否真正做到无明末硬编码。已看到日历外置和剧本路由，同时也看到 `+1627` 等残留。

附带文件状态：当前包的 `game-config.json`首字节为非JSON控制字节，而修改前备份以正常 `{` 开头；本轮没有修复或启动验证其影响。相关内容解析失败时客户端有默认配置回退路径，但不能把存在外置配置就说成当前所有Mod日历均实际生效。

本轮没有新增玩法代码。后续主任务应根据用户方向把经营底座与剧本包规则先整理清楚；原型已完成的保存、隔离、幂等、原话与来源能力可以保留作基础设施验证，不能将有限首片直接当成最终玩法边界。
