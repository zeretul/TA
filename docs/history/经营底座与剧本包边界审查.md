# 经营底座与剧本包边界审查

更新：2026-11-06。范围：只读核对当前TA历史原型和既有研究，提出规则与职责边界；本轮不改程序、界面、模型配置，不再扩充演示玩法。本文是后续统一规则书的审查输入，不另立一套已定稿规范；下文建议字段均为概念约定，不代表已经发布的接口。

## 一、结论与用户最新口径

经营玩法应采用**通用底座＋剧本包**。主循环是：玩家可先召见/廷议，也可直接下诏；AI结合整个世界的当季局势、既有命令和人物行为推演，形成季度奏报；玩家据此调整、撤销或继续命令，再进入下一季。讨论不是必经关卡，每季也不应要求把仍然有效的旧命令重新写一遍。

**当前原型验证了独立存档、交互、议事来源、正式确认、资源记录和恢复路径，不是上述通用经营游戏的最终设计。** 它既有应保留的可靠基础，也有为短流程验证而刻意写窄的明末规则。不能把这套规则直接定为经营底座，再不断添加明末特殊分支。

三国、崇祯属于经营方向，后续由各自剧本提供人物、势力、资源、制度、局势和目标。用户指定的低武紫川仍属冒险方向；不因它涉及战争与政治而自动迁入经营玩法。

既有研究依据：[两版参考与后续取舍](两版参考与后续取舍.md)与[独立模块和大臣记忆方案](../历史推演_独立模块与大臣记忆方案.md)。前者对原版客户端说明、自制系统和本地修改过的提示词已区分来源；没有官方服务器源码，就不能把客户端文案当成官方内部算法。

## 三、底座、剧本和本局分别拥有什么

建议只有三个清楚的责任层，暂不另建庞大的插件框架。

| 责任层 | 应拥有的内容 | 不应承担的内容 |
| --- | --- | --- |
| 通用经营底座 | 稳定实体ID、命令来源与版本、季度提交、记忆和知情投影、取消/重试/并发、资源账目一致性、存档与恢复；调用不同职责的AI；通用议事/下令/奏报交互。 | 明末四大臣、某年的账面金额、固定税率/例支、陕西灾情、特定朝代官制、任何剧本必须只有三种政务。 |
| 剧本包 | 初始世界、势力与控制范围、人物和机构、资源/计量、经济与政治规则、事件发展条件、情报制度、阶段目标/结局、时代语气和本地化展示。 | 私人模型凭据、真实用户存档、依赖宿主绝对路径的身份、任意执行脚本或覆盖底座提交/保密规则的指令。 |
| 本局正式状态 | 此局实际发生的变化、现任人物与职务、已颁命令和有效政策、当季账目、世界势力行动、事件进度、已经送达的报告、个人经历与承诺。 | 把剧本最新文件静默当作旧档事实；把模型提案或聊天承诺直接当成已执行结果；用新剧本覆盖另一存档。 |

底座共用“主体、地区、机构、资源账户、关系、命令、事件、报告”等少量概念；具体有哪些主体/指标、名称是什么、允许怎样变化，由剧本说明。不能把全部内容降成无约束JSON：需要跨季追踪和守恒的事实应有稳定身份与明确类型，但无需把每一种政策都写成一个Go分支。

下面是内容分类，不要求立即创建这些目录或文件。

**兼容底线：** 同一底座载入明末或三国，不修改通用程序，也不自动带入另一剧本的人物、官制、资源单位和事件。两个剧本可以共享规则主题，但各自绑定明确版本；不能仅依包名猜测拥有哪种能力。

## 四、把主循环写成可判断的规则

### 1. 议事和直接下诏都是合法入口

- 议事可以问局势、追问奏报、比较方案、明确分工，也可以结束而不下令。
- 直接下诏无需先找大臣“解锁”。AI应理解整段自然语言，包括目的、优先级、授权、预算边界、条件、持续时间和撤销意图。
- 讨论中的建议只在玩家采纳时成为待批方案；当前已经保存的`source_chat_id`可作为通用来源机制的基础。后续来源还应能指向特定奏报、旧命令版本或调查结果。
- 不要求玩家每次填完整表格。若玩家明确授权“由户部酌办，限额内处理”，规则应允许在授权内拟办；若涉及未授权的重大投入/冲突，则说明待定点。不能把所有自然委托都因缺少四个固定字段判成“不支持”。

### 2. 命令有持续身份，不随谈话摘要消失

一条正式命令至少应能回答：谁下达、基于什么、对谁/哪里、达到什么目的、允许采取什么、资源和权力边界、何时生效、何时终止、由谁负责，以及当前是哪一版。

建议生命周期为“拟议—待批—已颁/待条件—执行中—完成或失效”，并能保留暂停、恢复、修订、撤销与替代的历史。具体名称可在统一规则书压缩；关键是不能只剩一段文本和一个工程进度条。

- **继续**：原有效命令进入下季，不再重复创建、不重新扣一次总预算。
- **修订**：记录新版本及与旧版的关系，只修改玩家明确改变的部分；既有成果、已付代价和未了责任继续保留。
- **撤销**：从明确的生效时点停止未来执行；已花的钱、已造成的民情和外交后果不因撤销自动恢复。未用专款如何退回由剧本的财政规则确定。
- **暂停与恢复**：保留责任和既有投入，说明维护/停工代价。暂停不应被偷偷解释为永久撤销。
- **长期国策**：没有“工程完工”这一必要终点；每季持续影响世界，直到到期、被修订/替代或撤销。它可以引发后续项目，但不能等同于单个项目。
- **回溯存档**：是玩家的存档操作，不是君主在世界内撤销政策，两者必须分开。

### 3. AI从全局局势推演，不只给工程加减分

季度推演至少应看见：剧本规则及时代边界、世界实体与资源现状、各势力目标/行动条件、全部有效命令与政策、进行中的事务、关键历史因果、未解决危机/承诺和本季时间范围。

全局不等于把所有原始对话无限塞入上下文。应保留唯一正式记录，生成可追溯的现行世界视图；相关旧事检索带来源，未解决命令/政策/危机必须常驻有效视图。当前192KiB输入上限（`history_model.go:18–31`）是保护边界，不是世界规模方案；正式规则需要说明超限时怎样分层摘要、保留重要状态和披露缺漏，不能悄悄丢掉仍有效的政令。

全局推演者可以使用世界真实状态；对玩家和不同大臣显示的消息须按知情规则过滤。不得因为大臣不知道前线消息，连推演者也不知道；也不得因为推演者知道全部事实，就把敌方隐情和所有私谈放进每位大臣口中。

AI负责推演世界反应、人的选择、执行偏差、矛盾、事件发展和后续影响；程序检查身份引用、资源与权限边界、因果记录和提交一致性。三种工作类型和±3灾情不能成为AI的永久能力边界。

### 4. 季度结果一次核定，再形成各人的奏报

拟议结果应包含本季实际变化、资源流向、命令执行情况、其他主体行动、事件阶段变化、重要因果和下一季遗留问题。每项结果都能追到命令、既有世界趋势或本季其他主体行动，不能靠一句正文凭空改变国库、官职或战争结果。

底座校验后一次正式保存本季结果与新季状态；失败或取消不留下半季。数额来自正式记录，报告不能二次结算。当前“先核定、后叙述”的方向应保留，但核定对象需从三项工程扩展为通用世界变化。

大臣奏报是带作者、时间、对象、知情范围和来源的视图。若剧本允许迟报、误判或瞒报，必须区分“世界实际发生”“报告声称发生”和“皇帝当时知道”，并给出可追查的线索；不要把每次AI措辞偏差都当成合法瞒报。

### 5. 奏报推动下一轮决策

每条要事应能联系到责任人、原命令/政策和可继续讨论的议题，供玩家直接召见、修改原令、撤销或保持不变。后续入口传递稳定来源身份和当季状态，不要求玩家手工复制报告，也不在背后新增重复命令。

“保持不变并进入下一季”本身是一种有效决策：旧政策继续运行，外部局势继续变化。不能把无新诏令的一季当作没有任何世界变化。

## 五、建议保留的最小概念约定

不先铺设新的复杂框架，可先在统一规则书中确认以下六种记录。它们是说明游戏真相的方式，不是要求现阶段立即新增六套数据表。

| 记录 | 最少应表达什么 | 不允许混淆什么 |
| --- | --- | --- |
| 剧本绑定 | 剧本ID/版本/内容摘要、适用规则、开局选择。 | 最新包文件≠旧档当前事实。 |
| 世界事实 | 主体/对象、属性或关系、值/状态、有效时间、来源；需要时区分真实与报告值。 | 对话推测≠正式事实；旧余额≠当前余额。 |
| 命令/政策 | 稳定ID、版本、自然原意、来源、范围/负责人、授权/资源边界、条件/期限、状态及修订/替代关系。 | 提案≠生效，继续≠重发，撤销≠回档。 |
| 季度变化 | 输入世界版本、拟变更、成本/收益来源、因果、实际执行状态、生成的下季事实。 | AI描述≠已提交结果；同一钱粮不能被重复消费。 |
| 信息/记忆 | 发出者、接收者、形成与送达时间、所指事实/命令/事件、当时说过的话。 | 全局真相≠所有人的共同知识；摘要≠唯一存档。 |
| 事件/目标 | 当前阶段、触发和退出条件、已知预警、可干预点、期限与实际结果。 | 真实历史结局≠本局注定结局；倒计时≠仅装饰文案。 |

资源变动需要明确来源与去向；生成收入、消耗、损失、转换等应有规则依据。不是简单要求全世界所有数字相加恒定，也不是允许模型任意加减库存。这里适合保留少量通用校验，具体经济因果优先通过剧本规则和AI来决定。

“未知命令”应区分三种情况：玩家意图需澄清、剧本时代/权限不允许、当前底座确实无法表达其结果。第一种补问题，第二种按世界规则解释阻碍，第三种才列功能缺口。不能全部用`unsupported`掩盖成同一种失败。

## 六、下一步应先完成的规则工作

1. **先定统一经营规则书。** 以“世界状态—有效命令—全局推演—奏报—命令修订”串起原版/自制版有价值的机制；明确底座不负责哪一朝代的具体事实。不继续以赈济首片覆盖整个产品定义。
2. **以明末、三国两份内容清单检验规则。** 比较玩家权限、势力、官制、资源、军事与外交、事件及目标，先做纸面规则映射；若同一条底座规则只能用明末词汇解释，就继续调整边界。此阶段不新增可执行演示包。
3. **先写持续政策和全局因果的例子。** 一条无需重复下令的税政/后勤政策、一条修订/撤销有残余代价的命令、一项外部势力行动如何影响本季；说清前后状态、知道的人及报告来源。让例子暴露规则缺项，而不是只补好看的叙事。
4. **再决定必要的最小程序改动。** 已验证的存储、来源、确认、并发和取消继续复用；只有自然规则无法可靠保存身份、持续状态、资源和正式结果时才改代码。不要为每条诏令单独造按钮、API或算法分支。

## 七、交付口径与审查边界

可以继续表述为“0.7.0基线上的独立经营原型已验证若干交互与持久化性质”；不得表述为“经营通用底座已完成”“明末完整世界已完成”“三国可直接换皮使用”或“全局推演只差美化”。

当前最容易被遗漏的实质问题是：剧本版本没有绑定、AI能影响的状态过窄、有效国策缺少独立持久身份、世界全局与各人知情未形成完整分层、奏报尚不能自然驱动原命令的修订。这五项影响实际玩法与长期一致性，应进入规则设计；持续试玩和一般验证不作为功能缺项凑数。
