# TA独立历史推演：开发方式、大臣聊天与界面方案

更新：2026-11-06。状态：已从baseline/0.7.0建立feature/history-simulation工作树，首个明末闭环已实现并原生验收，尚未安装到正式目录；现状见历史推演_首轮开发与验收.md。以用户最新分类为准：三国、崇祯归经营；紫川归低武冒险。

## 开发方式

推荐同仓库、独立历史模块、单独分支和工作树。先以已固定的0.7.0源码基线及完成验证的世界适配修复作为起点，再创建历史推演工作树。已完成Git精简和0.7.0基线对齐，后续从baseline/0.7.0开工。参见[开发基线](0.7.0_开发基线.md)。

工作树隔离的是开发过程，游戏模块隔离的是运行时。最终仍可由同一个TA启动入口选择冒险或历史推演；二者共用模型配置、语言主题、流式显示、取消重试和通用存储能力，使用独立的游戏状态、时钟、存档类型与界面。不需要先做一个与TA完全脱节的新项目再整包拼接。

## 保留已有机制

用户自制历史模拟器已有国库/粮食、军政、官员能力、长期项目、党派、灾情、历史压力、奏报与核查等设计。应保留有价值的功能和行为，优先重整UI及关键连接，不为了统一技术栈先重写所有经营公式。

原Python代码作为受保护的参考实现和行为对照。首批选择把赈济、练兵、跨季工程与修订的必要规则迁入独立Go模块，并接入TA现有模型配置；不包装整个旧Python引擎，避免旧全局数据路径、异常吞掉和模型入口与新存档事务混用。旧完整军政、党派、外交等系统没有因此被宣称全部移植。

## 大臣聊天是核心玩法

单独召见与多人廷议都保留。聊天可以咨询、追问奏折、询问执行进度、讨论方案、形成承诺与拟旨；正式诏令仍由玩家确认颁布。聊天承诺不直接增加国库或完成工程，执行结果须进入季度正式记录。

旧项目已有：
- npc_memory.py保存互动、承诺和经历，并按议题检索。
- court.py每轮重新读取事实，支持针对奏折召见及多轮御前议事。
- 正式发布与讨论分开，并有重复发布检查。

因此改进方向不是重做一个“有聊天框”的页面，而是让人物在跨季度、换话题和重开后持续承接真实经历。

## 记忆与局势的组合

每位大臣的一轮上下文由五部分组成：
1. 稳定身份：官职、职责、能力、性格、利益和当前关系。
2. 当季已收到的局势简报：正式季度与已生效政策；人物有渠道获得的情报。
3. 负责的事务：任务现状、资源、期限、上一回合实际结果。
4. 可追溯个人记忆：相关旧承诺、争执、恩怨、执行经历，保留来源和当时日期。
5. 最近谈话：当前议题与刚才说了什么。

“了解局势”不等于知道全部国家秘密。户部官员掌握应知钱粮，前线将领知道已送达军报；未收到的变化明确说尚待回报。密谈按实际受众保存，廷议只共享应公开的事实。

旧实现需要补强：
- 摘要按层级上限8/32/80清理，连续中文串完全匹配的检索对近义表达不稳；原始议事历史仍保留，不能说历史已全部删除。
- 聊天只取最近8条，旧承诺要靠长期索引找回；压缩上下文不能删除唯一事实来源。
- 旧对话数字被加入允许数字白名单，可能在当季国库已改变后仍被视作合法。当前事实应优先，旧话标记“当时说过”，不能当成当前账面。
- 多人个人记忆合入一次提示词，缺少职责、收报时间和秘密受众过滤；这属于代码路径风险，本轮未声称观察到真实模型泄密。

可借用TA已有Knowledge的来源、持有人、受众、替代/撤销与有效记忆视图，建立历史游戏适配。不要把国家状态强塞进冒险人物背包。

## 界面重做方向

保留功能，改变入口层级。主界面围绕本季要事、国势与地图、奏报、召见/廷议、诏令、长期政策展开。军队、财政、军工、派系等作为能展开的专业明细，避免每季操作一排部门页面。

召见页突出大臣、当前议题、当季信息、相关政策和未了承诺，提供“拟成诏令”。廷议允许选人、追问与总结，不强制全员轮番发言。季度结果先交代哪些命令执行了、哪些受阻及为什么，再展开数字和奏报。

AI实质承担整份诏令的意图拆解、条件与依赖、人物反应、执行偏差、外交和局势演化。系统核对资源守恒、时间、权限和状态一致性，负责正式保存及重试。不能把AI降为固定按钮文案，也不能凭一句成功叙述改变已保存事实。

## 首批可评审闭环

先做一个明末剧本的完整短周期：多条复合诏令、条件执行、一个可修订的跨季度项目、一次奏报质询和核查、至少一条可干预危机、保存重开与失败重试。保留旧南宋资料作后续复用，不把active清单当成TA已经完成移植。

实测重点：同一大臣跨季度记得旧承诺；新账面覆盖旧数字；密谈不泄露；三条命令逐条有结果；未到条件的政策不提前完成。UI应同时核对桌面、窄屏、长诏令和多轮聊天。
