# 0.7.0 底座＋世界包定向细查（2026-11-07）

## 结论与范围

**发现 5 类适配缺口，尚未修复。上一轮“四包已统一”的结论不能扩大为“自定义世界适配已完成”。** 四个内置包的现有数据可以使用；问题集中在裁剪/导入包、特殊机制的开局状态，以及自然语言核心规则的上下文通路。

本轮按用户要求做定向审计，不用全量测试通过率替代边界检查。反例通过临时 Go overlay 运行，生产源码、三套安装和私人配置未修改；原 295 个源码文件哈希复核一致。历史推演工作树、共享依赖与代理服务未改。

## 1. P1：自定义世界无法通过正常开局申请新机制字段

- 入口：`internal/storypack/request.go:56`。`Pack.StoryRequest()` 无条件设置 `fixed_template`。
- 后续：`StoryStateSchemaPolicyUsesOpeningGameAgent` 因而返回 false；开局状态适配工具/说明不启用。
- 反例：通过真实 `WorldDraft.BuildPack()` 创建需要记录“承诺内容、见证人、成立时间、期限、履行状态”的规则包，读取其正式建局请求；结果仍是 fixed_template。
- 影响：底层已有添加 string/bool/enum/object/list 等字段的能力，但新世界的正常入口没有使用它。需要独立跟踪的机制只能被迫放入已有字段/本局文字，或另走手工配置，不能据此声称完成了自动适配。
- 上轮覆盖不足：`world_narrative_mechanism_test.go` 手工预先加入了“特殊状态”字段，再验证保存/分支/冷重开；它没有经过世界包建局策略，无法发现这个问题。
- 最小修复方向：让需要 AI 建立状态的通用世界复用已有开局适配流程；保留既有精确结算字段的保护，不一刀切允许模型改写所有数值结构，不另造“誓约系统”。

证据：`TestDeepAuditNewMechanismCanRequestOpeningStateAdaptation`，`boundary-probes.log` / `final-probes.log`。

## 2. P1：核心世界规则可能完全漏出本轮模型上下文

- 生成端：`internal/app/story_pack_world_draft.go:292` 的模型答复条目只接收 name/type/brief/content，不接收关键词和取用方式。
- 保存端：`internal/storypack/world_draft.go:919` 将未指定取用方式的条目设成 auto。
- 取用端：`internal/app/interactive/lore_context.go:302` 在没有匹配关键词时直接跳过索引取用；按名称取用又要求玩家话里出现条目名。
- 反例：正式构建并写入一个 `type=rule` 的“灯印规则”，包含“自愿＋真实见证人＋灯亮才成立，熄灯不取消既有约定”。普通行动输入“我自愿明天归还借书。”。实际条目为 `load_mode=auto, keywords=[]`；常驻资料和本轮工作集都不含该规则，选择记录为 `selected=0`。
- 影响：规则写在世界书里，不等于 AI 在推演前一定拿到。模型仍可能主动调用读取工具补读，故本轮不声称它必然违规；但目前缺少核心规则必达保障。
- 最小修复方向：复用已有 resident/auto/manual 机制，区分必须遵守的基础规则与情境资料；生成与保存流程保留明确的取用信息，关键词服务按需资料，不让它成为核心规则唯一入口。保留既有容量限制与知情过滤，不能简单把整本世界书常驻。

证据：`TestDeepAuditGeneratedCoreRuleReachesOrdinaryAction`，`final-probes.log`。

## 3. P1：裁剪后的合法修仙包会建包失败或无法再次加载

- 入口：`internal/storypack/world_gameplay_modules.go:41` 比较已有模块与本次生成模块的内容哈希。
- 根因：模块生成时换入自己的 CultivationRules，但继承模板中的说明尚未按新目录整理；`ActorStateLibrary.Create/Get` 会通过 `normalizeActorStateSystem` 重新生成物品说明、技能模板说明和阶段选项。比较的两侧不在同一个规范化阶段。
- 反例 A：清空物品和配方目录，规则校验通过，第一次构建成功；第二次构建同一份未改动的包，报 `world state module ... differs from its pack definition`。
- 反例 B：只清空生成技能模板，同样第二次加载失败。
- 真实保存入口：`Library.SaveWorld()` 使用清空生成模板的自定义修仙包，也复现相同错误，不是仅有内部 helper 的合成问题。
- 影响：作者不能可靠地删去不需要的既有机制；四个内置包使用参考目录恰好掩盖了此差异。
- 最小修复方向：模块生成、保存、读取和哈希比较共用同一规范化结果；不能通过恢复被删目录或忽略哈希不一致来“修复”。

证据：`TestDeepAuditTrimmedCultivationModuleRoundTrip/items`、`/skill_templates`、`TestDeepAuditPublicSaveWithEmptySkillTemplates`。

## 4. P1：缺失规则快照仍可退回程序默认表

- 入口：`Rules.Validate(nil)` 返回 nil；修仙包能力组合满足后 `ValidateWorldGameplay` 直接放行。
- 模块构建：`world_gameplay_modules.go:114` 将缺失的 CultivationRules 原样设成 nil。
- 消费者：例如 `internal/cultivation/item_catalog.go:517` 在参数为 nil 时读取程序默认目录，修炼计算器也保留这种参考调用方式。
- 反例：包仍声明修仙能力和自己的 WorldContent，但移除 CultivationRules；包校验、模块创建、读取均成功，结果为“启用了修仙，但本局没有参数快照”。
- 影响：这条导入/载入路径没有保证数值与目录冻结。将来程序默认表变化，可能改变这类包的行为。
- 已区分的正常路径：`WorldDraft.BuildPack()` 在用户明确选择修仙模板时会复制参考参数到包里，这本身不是问题；缺口是其他载入路径仍接受参数缺失。
- 最小修复方向：绑定世界运行时要求完整、明确的规则来源；缺失应在载入时拒绝或经过明确的模板复制，不能静默回退。无需重写计算器，也无需为本轮试玩旧档增加复杂兼容。

证据：`TestDeepAuditCultivationSnapshotCannotOmitRules`。

## 5. P1/P2：包内引用和能力声明缺少完整交叉校验

### 知情限制可因换 ID 失效（P1）

`WorldContent.Validate()` 检查限制引用的地点，却没有确认 `LoreGates` 的条目 ID 存在于包的 World 中。

实际反例：仅将“通往灵界的远行”的条目 ID 改成新 ID，保留原知情限制。包校验仍通过；实际 `WorldInputs()` 生成新条目 ID，而过滤器仍阻止旧 ID。没有阶段和地点资格的读取方，现可通过该过滤器。

这是限制失效的实证，不只是多了一个无用配置键。修复应校验引用并保持条目稳定身份；不能让限制失配自动变成开放。

### 未实现的能力声明被接受（P2）

将修仙包的 communication 改成 `unimplemented-telepathy`，或 opening 改成 `unimplemented-mode`，`ValidateWorldGameplay()` 都返回成功。该分支在检查这两个字段前直接返回了。

修复应统一检查受支持声明并给出明确错误，不把它降级成其他玩法，也不借此新增心灵感应或专用开局引擎。

证据：`TestDeepAuditRenamedLoreCannotBypassKnowledgeGate`、`TestDeepAuditRejectsDanglingLoreKnowledgeGate`、`TestDeepAuditCultivationRejectsUnknownCapabilities/*`。

## 建议修复次序

先修核心规则取用和通用世界开局适配，再统一模块规范化与参数来源校验，最后补齐引用/能力交叉校验；全部复用现有流程。随后按已准备的“灯印”案例跑真实 WB：缺灯不成立 → 三条件齐备成立 → 熄灯不取消 → 到期前不算违约 → 重开/分支仍保持事实。不要先扩展新的专用玩法程序。
