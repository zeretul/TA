# 集成点与后续迭代

本文登记**本版尚未实现的功能**，以及它们将来要接的话应该接在哪里；对已经实现的功能，则登记它的实际实现位置。第一、二、三节属于后者。

> **性质声明：本文是接入位置登记，不是实现报告。**
> 下文出现的每一个文件、类型、函数、行号，都是**当前仓库里已经存在的真实代码**——它们原本就在原版里，用于支撑已有的通用能力。本文只说明「这些现成的缝在哪里」，**除已注明「已实现」的节外，不代表其余功能已经实现**。

七项功能中，**独立 NPC 私聊、完整修炼数值引擎、完整战斗三项已实现**（分别见第一、二、三节）；其余四项仍未做：

1. 关系 / 双修
2. 完整立绘与视频
3. 公共事件
4. 宗门指令

## 零、共同的地基：Story Director 模块系统

七项功能里有几项最终都要落到同一套模块系统上，所以先讲它。

**模块不是 Go interface，而是磁盘上的 JSON 文档**（经 `revisionjson.Store` 读写）。每一种「模块种类」遵循同一套模式，新增一种玩法模块 = 四处改动：

| 要加的东西 | 加在哪 |
| --- | --- |
| 一个 Module 结构体 | `internal/interactive/director_modules.go`（对照 `EventPackageModule`:80 / `RuleSystemModule`:96 / `ActorStateModule`:113） |
| 一个 Library（`List`/`Get`/`Create`/`Update`/`Delete`/`ensureBuiltins`/`dir`） | 同上（对照 `EventPackageLibrary`:129 / `RuleSystemLibrary`:133 / `ActorStateLibrary`:137） |
| 一个内置注册函数 | 对照 `builtinRuleSystemModules()`:653、`builtinEventPackageModules()`（`event_system_presets.go`:30）、`builtinActorStateModules()`（`actor_state_presets.go`:40） |
| 一个 ID 常量 + `StoryDirectorModuleRefs` 里的一个字段 | `director_modules.go`:24-33（常量）、:42（`StoryDirectorModuleRefs`） |

其他相关件：

- 模块种类共五种：叙事风格（存于 `teller` 库）、事件包、规则系统、角色状态、图像预设。
- `NormalizeStoryDirectorModuleRefs`(:379)、`DefaultStoryDirectorModuleRefs`(:369)、解析引擎 `ResolveStoryDirectorModules(novaDir, director)`(:420)。
- `StoryDirectorResolvedSnapshot`(:64) 是解析后的「最后已知可用」展开图，带 `Warnings`，让引用被删/改名/失效时 preset 与 story 仍能运行。
- 校验入口：`validateEventPackageModule`(:982)、`validateRuleSystemModule`(:1007)、`validateActorStateModule`(:1025)。
- 内置判定：`IsBuiltinEventPackageID` / `IsBuiltinRuleSystemID` / `IsBuiltinActorStateID`(:788-798)。
- 目录布局：`internal/presetlayout/layout.go` — `Root`(:10)、`NarrativeStyles`(:14)、`EventPackages`(:26)、`RuleSystems`(:30)、`ActorStates`(:34)、`Image`(:18)、`StoryPacks`(:42)。
- 前端选择 UI：`web/src/features/interactive/components/director-console/StoryTuningModuleRows.tsx`（`ModuleSelectRow`:26、`EventPackagesRow`:49）；预设编辑区 `web/src/features/interactive/components/preset-config/`。

**结论：任何新玩法（数值、战斗、关系、公共事件、宗门）都应从「加一种模块 / 加一个内置 ID / 在 `StoryDirectorModuleRefs` 加一个字段」入手，而不是另建一套并行的可写世界状态。** 这是本包在剧本包里已经遵守的同一条硬约束。

## 一、完整修炼数值引擎

**现状**：**已实现。** 本批新增 `internal/cultivation/` 规则层，实现了《自制-修仙数值规则》V0.3 的确定性数值：境界表与派生属性、连续修炼积累、大境界突破、统一来源预算与上限。规则层不读不写 journal——调用方传入当前值、取回变更，再由故事自己的原子提交路径落库，因此离线仿真、故事回合和战斗回合共用同一份规则，三者不会对同一件事给出不同数字。

**关键性质：派生数值不落库。** journal 只存境界键与真实当前值（当前生命／灵力）；上限与四项派生属性每次展示或使用时按规则重算。这正是「模型不得改写角色修为」这条约束能**结构性成立**、而非靠指令约束的原因——没有可供改写的存档数字，也没有第二份会漂移的副本。当前值确实要存，因为伤势是境界表无法重建的真实事实。

## 二、完整战斗

**现状**：**已实现。** 本批交付了专用战斗系统：战斗循环、命中／伤害模型、先攻序列、撤退与投降等非击杀结束路径、物品使用，以及独立战斗窗口。战斗在**窗口里逐回合结算并作为侧记录写进同一条 Story JSONL**，回合先由规则判定、再由模型据已判定事实写演绎（§6.6「AI 在规则之后」）。

**关键性质：随机数由调用方传入。** 先攻、命中与伤害波动都绑定请求身份（`CombatRolls`），所以重试、刷新或重开窗口**复用同一次抽样**而不是重掷。规则层不自己抽随机数，这条性质因此是结构性的，不是调用方可能忘记的约定。

## 九、做这些功能时要守住的东西

本包已经证明过一条路走得通（剧本包），后续迭代沿用同一套约束：

1. **不新增第二条创建通路。** 新玩法往「模块」里加，故事仍由原版 `createInteractiveStory` 创建。
2. **不新增第二条状态提交通路。** 一切状态变化走 `AppendTurnWithState` 与 `TurnStateRevisedEvent` 这类既有 append-only 缝。
3. **不迁移存储。** 保持 DENOVA 原生 JSON / JSONL + journal，不引入 SQLite，不另建可写世界状态。
4. **不覆盖用户成果。** 参考剧本包写世界书的做法：按名去重、幂等、不冲掉手工编辑。
5. **不删能力。** 参考精简游戏入口的做法：只改默认可见性，不删入口、不留悬空依赖。
